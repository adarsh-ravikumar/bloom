# Application Pipeline

## Svelte + Tauri

- This is the UI layer
- Tauri receives/sends data from/to the bloom host

## Bloom Host

- This layer acts as the bridge between the UI layer and the Data layer
- Data is sent/recieved over a TCP socket.
- This layer is implemented in Rust

## Bloom client

- This is the data layer.
- Users write logic here to serve data from their application / react to state changes etc.
- This layer is language agnostic. API available for the particular implementation language should be used
- The language of the bloom client and the actual application for which bloom is being used will be in the same language
- This is done so that the user simply includes their application, and drive it from within the Bloom client.

## Packet structure

```
Payload Size(=n) | Panel ID | Specifier | Payload (JSON)
[    4 bytes    ][ 4 bytes ][ 4 bytes  ][   n bytes    ]
```

- Payload Size (=n): Size in bytes of the payload
- Panel ID: Source in case of event, Destination in case of command
- Specifier: Event / Command ID
- Payload: n bytes of data, in JSON format

- Every communication between the bloom host and client are modelled as events or commands

## Connection

- The client connects to the host layer through the custom TCP protocol.
- During connection, the client looks for a set of fixed ports. If any of them is alive, it sends the connection packet
- The connection packet consists of the app name, client version and a unique client ID
- A bloom host can only have one client at a time. This is purely to avoid race conditions / multi-client sync problems.
- If the client is valid (version, app name etc.), it is now connected. The bloom host no longer accepts any further clients.

## Synchronization

- The API's workspace instance will now actively sync to the UI layer's workspace.
- It holds a map of what panel instances are alive by type.
- It also holds a map of command/event name -> ID. This ID is unique to the panel type, not induvidual instances.
- This ID is generated by the UI layer. The client simply holds a copy of it.
- Semantically, this allows for the client to do things like:

```
inspector = workspace.panel("inspector").instance(2)
inspector.command("exploreElement", [...])
```

- The string then resolves to the ID.
- The client API will also allow for broadcastin over all instances, like:

```
inspector = workspace.panel("inspector")
inspector.command("exploreElement", [...])
```

- Where this invokes the `exploreElement` command on all `inspector` instances
- This is done serially, by order of registration

- The client can request the creation / destruction of a panel in a similar fassion.

```
my_inspector = workspace.create_panel("inspector") 
```

- This will send a `create_panel` command to the host, and once the panel is created, the ID is sent back to the client and registered in the workspace

# Architecture

- Every bloom app has exactly one Workspace
- The workspace is responsible for the lifecycle of Panels
- Panels are opaque structures that composes and abstracts the commands & events of widgets
- Panels are responsible for the lifecycle of Widgets they compose
- Widgets are the atoms of a bloom application. They model UI behaviour, events, and commands.

## Workspace

- Owns:
  - Panel Registry
  - Transporter
  - Theme manager

## Transporter

- Consumes the `Global event stream`, and emits events to `Tauri`, from where further handling is taken care of by the host.
- Exposes a resolution callback to `Tauri`, which is then responsible for dispatching the right command from the `Global command registry`

## Panel

- Owns:
  - Widgets
  - Semantic Command & Event wrappers. These can either be just "re-labels", or they can also augment the data going into and out of widgets

- It is these "wrappers" that the transporter emits / invokes

## Widget

- Owns:
  - Commands
  - Events
  - UI implementation
  - Styling
